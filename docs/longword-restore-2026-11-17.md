# 碎片 → 长词还原与补入（第 5 轮）

日期：2026-11-17
任务：把碎片对应的完整长词还原出来补进词库，让分词优先切长词、碎片不再当入口
上游：第 4 轮碎片清理（`docs/fragment-cleanup-2026-11-17.md`）

---

## 0. 结论

| 问题 | 答案 |
|---|---|
| 还原出多少长词 | 3030 条碎片（出现≥10 次）→ 可还原 338 → 语义确认 **155** |
| 试点补了多少 | **100 条**（出现频次最高的那批） |
| 碎片对降了多少 | 3556 → **3533**（-23，**-0.65%**） |
| 120 例效果 | **95**（基线 95，持平，不退化） |
| 值得继续吗 | **不值得全量补**。收益 0.65%，且 43% 的新词根本没参与分词 |

**一句话**：长词补进来的价值在「用户能打出这个词」，不在搭配表。
搭配表的瓶颈不是词库覆盖，是**分词窗口只有 4 字**。

## 1. 阶段 1：语料还原（只读）

脚本：`tools/restore_longwords.py`（新增）

口径（任务书 1.1）：碎片向长词方向延伸 1~4 字，统计每个延伸串的 `total_occ` 与
`standalone`（前后都不是汉字）；取 `standalone ≥ 3` 且 `standalone/total_occ ≥ 0.5`
且 `total_occ` 最大的串。

```
碎片（occ >= 10）: 3030
语料: 76.8M 字，延伸串 373,746 个
可还原 338，不可还原 2692
还原词字数分布: {3: 21, 4: 127, 5: 93, 6: 57, 7: 33, 8: 7}
```

产物：`tmp/longword_restore.tsv` / `tmp/longword_candidates.tsv`

### 1.1 噪声有多大

338 条可还原里，**183 条不是词**，是句子片段：

```
上载 → 已上载        日凌 → 日凌晨       积为 → 区域总面积为
汉族人 → 汉族人口为   动到 → 的讨论移动到  节假日 → 节假日和习俗
```

根因：「碎片 + 紧跟字」常常只是跨词的邻接关系，语料统计分不清「词的第二个字」和
「下一句的开头」。**纯统计还原的精度只有 46%**，语义确认这步不能省。

## 3. 阶段 2：试点补词

### 3.1 词条落点与拼音

- 清单：`curate/longwords.txt`（词 / 拼音 / 频次），`pipeline.py` 在融合阶段补入（已存在跳过）
- 拼音：`pypinyin` 注音，**连写无分隔符**（与词库现有格式一致，如 `tiananmenguangchang`）
- 频次：按语料出现次数分档 1000 / 800 / 600 / 500，**刻意低于同类 5~7 字专名的常见档位
  （1500-3000）**，避免长词抢短词的首位

脚本：`tools/add_longwords.py`（新增，支持 `--dry-run`）

### 3.2 一个必须记下的 bug

首轮执行时 `INSERT INTO system_dict (pinyin, word, frequency) VALUES (?, ?, ?)`
的列名顺序与值元组 `(word, pinyin, freq)` 颠倒，100 条词写成了「词 = 拼音」。
发现方式是重跑搭配表后词表数没变（355,568 → 355,568），追查 `typeof(word)` 才定位。

已删除污染行（`DELETE WHERE id > 372733`）并修正列序，重新插入。

### 3.3 补词结果

```
清单: 100 词，待补 100，已存在 0
已补入 100 词；库内词条共 372,833 条（原 372,733）
1-4 字唯一词数: 355,568 → 355,609（+41）
```

注意 +41 而不是 +57：16 条 3~4 字词在库里已存在（不同拼音），补入的是新读法。

## 6. 为什么收益这么低（根因）

三个叠加的硬约束：

**① 分词窗口只有 4 字**（`build_context_prior.py` 的 `WORD_MAX_LEN`）。
补的 100 条里 43 条是 5~8 字，**根本没进分词词表**，对搭配表零影响：

```
词表: 355,609 词（1-4 字）
补入 100 条中：3~4 字 57 条（进词表），5~8 字 43 条（不进）
```

**② 进了词表的 57 条也大多没改变切分**。补词后搭配表只变动 9 对（385,983 → 385,992），
说明这 57 条词在语料里的分布，没有形成「原本切碎、现在能整体切出」的稳定模式。

**③ 放宽窗口已验证不可行**。第 4 轮测过 `--segment-max-len 8`：120 例从 95 掉到 93。

结论：**搭配表的质量瓶颈在分词口径与语料形态，不在词库覆盖率。**
继续补长尾长词的边际收益接近零。

---

## 7. 长词该不该补（分开看）

补长词本身有价值，只是价值不在搭配表：

| 维度 | 收益 |
|---|---|
| 用户能打出专名（马尔维纳斯群岛、仙剑奇侠传） | 真实，7/7 抽测验证 |
| 搭配表质量 | 近乎零（-0.65% 碎片对，120 例持平） |
| 候选排序 | 无负面影响（不抢首位，5/5 验证） |

建议：把 `curate/longwords.txt` 当作**按需补词通道**保留——发现用户打不出的专名就加一行，
不必追求「把 6442 条碎片都还原成词」。

## 8. 遗留

1. 剩余 55 条候选（155-100）未补，同属长尾，收益预期同样接近零。
2. 3412 条出现 <10 次的碎片未做还原（长尾更长）。
3. 分词窗口与语料的匹配问题仍无解：4 字窗口切不出 7 字词，放宽窗口又伤效果。
   若要根治，得改分词算法（如双向最大匹配 + 长词内部拆分），超出本轮范围。
4. `tools/restore_longwords.py` 的「延伸字含虚词」没有过滤，是噪声主要来源，
   下次用可先加虚词黑名单。
