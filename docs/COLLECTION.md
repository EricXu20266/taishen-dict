# 词库采集方法论

本文记录泰深词库的**外部语料采集**流程与实测数据，供复用和二次开发。

现有词库的三层来源（jieba / 维基分类 / THUOCL）覆盖了 51 万词条，但边界很清楚：

- jieba 词频来自新闻语料，日常打字反而低效（见 `curate/demote.yaml` 的 40+ 条降权规则）
- 维基分类靠人工维护，新概念收录滞后
- 新词、专名、垂类术语覆盖不足

下面三条通道互补，各自解决一段。

---

## 通道一：维基分类 API（已在用）

`sources/wiki.py` 通过 MediaWiki API 递归遍历分类，采集条目标题。

**实测（Category:人工智能）**

| 深度 | 页面数 | 保留 | 子分类 | 耗时 |
|---|---|---|---|---|
| 0 | 158 | 87 | 32 | 1.7s |
| 2 | 379 | 159 | 61 | 154s |

**问题**

- **429 限流是硬约束**。`REQUEST_GAP = 0.15` 实测连续触发 429，退避 8/16/24 秒仍卡住。21 个领域全量跑会被打断——这是词库长期停留在旧版本的实际原因。
- **只取标题，不读正文**：分类成员只能覆盖「有独立条目」的概念。
- **纯汉字正则过滤** `^[\u4e00-\u9fff]{1,6}$` 会丢掉混排词（`AGI时代`、`AI摘要`）和 7 字以上术语。
- **繁体未归一**：87 个保留项里 31 个是繁体（`人工意識`、`圖形處理器`），简体用户命中不到。

## 通道二：维基 dumps（离线全量）

`tools/collect/wiki_dumps.py`

下载 `zhwiki-latest-pages-articles.xml.bz2`（约 3.2 GB），流式解析，绕开 API 限流。

**下载**：支持 Range 请求，用 aria2c 多连接（`-x4 -s4 -m10`）。注意 Wikimedia 对并发连接有限制，8 线程会 429，4 线程稳定。

**解析**：`bz2.BZ2Decompressor` 按 8 MB 块流式解压，内存恒定；按 `<page>` 边界切分，提取 `<title>` 和正文里的 `[[Category:X]]`。

**实测（前 12 万页）**

| 阶段 | 数量 |
|---|---|
| 解析页数 | 120,000（425s，重定向 37,611） |
| 纯汉字标题（2-8 字） | 72,241 |
| 繁简归一后 | 64,853（救回 7,388 个繁体变体） |
| 与词库差分后新词 | 38,335 |
| 带分类标签 | 41,656 |
| 按 21 领域关键词分流 | 7,372 |

**关键：分类标签是 dumps 相对 API 的真正优势**

条目正文里的 `[[Category:计算机科学]]` 相当于免费标注，按 `domains.yaml` 的领域关键词匹配就能自动分流。候选量从 38,335 压到 7,372，且天然按领域切好。

**局限**

- 62% 的条目没有可识别的分类标签（维基分类维护本身稀疏）
- 关键词匹配有误判：`economics` 会命中「企业」类分类，混进 `一楼一凤`；`computer` 会混进 `世纪最佳进球`
- 全站标题差分出的新词 75% 是专名（人名/地名/作品名），必须分级处理

## 通道三：RSS 新闻（时效性最强）

`tools/collect/news_rss.py`

**源表**：`tools/collect/news_sources.json`，已实测 19 个中文源可用。

| 源 | 条数 | 类型 |
|---|---|---|
| IT之家 / 虎嗅 / 东方财富（2 个）/ 华尔街见闻 | 60–98 | 综合 / 财经 |
| 智东西 / 机器之心 / 新智元 / 量子位 | 10–20 | AI 垂类 |
| 国际能源网 / 钛媒体 / Solidot / 少数派 / 中新网 | 10–50 | 垂类 |

**抽词**：复用 `tools/mine_input_strings.py` 的三指标——凝固度 PMI + 左右熵 + 跨文档频次。

| 方法 | 候选数 | Top 60 质量 |
|---|---|---|
| 最大匹配 + 频次 | 535 | 全是虚词碎片（`也是`/`中的`/`点此`） |
| PMI + 左右熵 + 去重 + 虚词过滤 | 450 | 约 60–70% 是真词 |

**四个必须做的过滤**

1. **源新鲜度**：抓完检查 `pubDate` 中位数，7 天内为 0 的源直接判死。实测人民网科技 RSS 的 100 条全部是 2021 年的历史归档，不筛会得到一堆「新冠」「奥密克戎」「科技冬奥」。
2. **每源限流**：不限制条数时，东方财富两个源（188 条）会把 AI 垂类（10–20 条）淹没，候选全是财报词（`同比增长`、`前三季度`）。建议每源最多 20–30 条。
3. **文档去重**：同一标题在多个源重复出现会污染频次统计（「牛吃草」重复 10 次）。
4. **繁简归一**：维基和部分源繁简混排，不归一的话同一词会拆成两份统计。

## 三档分级：收，但分层

采集到的候选不是「收/不收」的二元判断，而是三档：

| 档 | 内容 | 落库位置 | 优先级来源 |
|---|---|---|---|
| A | 通用词 / 术语 | 对应领域（modern / computer_extra / sci_extra…） | `is_hot_domain` 白名单 → `domain_heat = 1` |
| B | 人名 / 地名 / 机构 / 事件 | `proper_noun` 域 | 非热域 → `domain_heat = 0` |
| C | 生僻字碎片 / 错误切片 | 丢弃 | — |

**为什么专名要收**

用户真的会打「刘秉义」「渤海船舶重工」「讯飞输入法」。不收是覆盖缺失，收了抢前排才是问题。

**低优先怎么实现**

引擎的领域候选排序是四段键（`engine/src/dictionary/mod.rs`）：

```
精确长度 → 词长 → domain_heat 降序 → 加载序
```

`is_hot_domain` 白名单里的领域 `domain_heat` 初始为 1，其余为 0。所以 `proper_noun` 只要不进白名单，同长度下自然排在热域词之后；打完整拼音仍能命中。

**新增领域时的坑**

`pipeline.py` 的 5.4 步是 `shutil.copy(curate/domains/*.txt → output/domains/)`——**同名文件直接覆盖**。

`computer` / `physics` / `chemistry` 等域是 wiki 采集产物（只在 `output/`），`curate/` 里没有同名文件。如果要给它们补词，必须用独立文件名（`computer_extra.txt`），否则下次构建会把 wiki 产物的 1,946 条整个覆盖成你补的 170 条。

## 流程总览

```
采集          过滤              抽词 / 分流         分级            入库
────────────────────────────────────────────────────────────────────────
RSS 19 源  →  新鲜度+去重  →  PMI/左右熵     →  LLM 三档     →  A→领域域
dumps 3.2G →  繁简归一      →  分类标签分流    →  判断        →  B→proper_noun
API 分类   →  噪声清洗      →  标题过滤       →              →  C→丢弃
```

**人力边界**

实测纯规则到不了终点：38,335 个 dumps 新词，规则粗筛（生僻字/专名后缀/长度）只剔掉 26%，剩下 74% 仍需语义判断。新闻候选 PMI 过滤后仍有约 30% 是碎片（`神舟十`、`国工`、`癌症前`），这些恰好是 LLM 一眼能判、规则判不了的。

分工：

- **脚本负责**：抓取、限速退避、繁简归一、PMI/熵计算、注音、去重、落盘
- **LLM 负责**：判断是不是词、值不值得收、多音字读音
